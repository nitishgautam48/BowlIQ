# BowlIQ: Full Engineering & Security Audit

**Scope:** every file in `bowliq/` (49 source files, about 10.5k lines including the lockfile). That covers the backend (FastAPI, pipeline, analysis, report), scripts, tests, the frontend (Next.js 16), configuration and dependencies.
**Date:** 21 Nov 2026. **Assumption (as requested):** the app is headed for production deployment.

**Method:**
* Static analysis: ruff (E, F, W, B, S, SIM, RUF, PERF, ASYNC rules) and bandit.
* Dependency audit: `pip-audit` and `npm audit`.
* Manual line-by-line review.
* Live tests against a running server.

Each finding is labelled **[VERIFIED]** (reproduced live), **[CODE]** (traced to a specific line) or **[CLEARED]** (suspected, tested, and found not to be a problem).

> **Context.** BowlIQ was built as a single-user app running on `localhost`. Many of the Critical/High findings below have no effect in that setting, but every one of them blocks a networked, multi-user deployment. The two scores in §10 reflect both views.

## 4. Performance analysis

| Area | Finding | Recommendation |
|---|---|---|
| Pose (CPU) | Dominant cost, about 0.07–0.1 s per 1280 px frame. A 30 s clip at 120 fps takes about 4–6 min on the single worker | Downscale the pose input to a 960 px long side (keeps accuracy at ~1.8× speed). Add RTMPose with onnxruntime-gpu for the RTX 4060 |
| Event loop | **[VERIFIED] H6**: `/api/health` stalled up to 139 ms while a 380 KB upload was probed; this scales with file size | Make `analyze` a sync `def` (it runs in the threadpool), or wrap blocking calls in `anyio.to_thread.run_sync` |
| Rendering | Two full ffmpeg encodes (annotated + clean) with frames repeated 4× in the slow-motion window | Encode the clean video with `-c:v libx264` directly from `side_prep.mp4` using an ffmpeg `select`/`setpts` filter instead of piping raw frames |
| `/frame/{n}` | Opens and decodes the video on every request, with no server-side cache | Cache JPEGs at `frames/{n}_{joint}.jpg`, and send `ETag` plus an immutable `Cache-Control` |
| Videos | Served with `Cache-Control: no-cache` although each file is immutable per id | Use `private, max-age=31536000, immutable` |
| DB | No N+1 queries (history is a single query). `_history()` parses every row's JSON on each job, O(n) per bowler | Add an index on `(bowler_name, created_at)` and `LIMIT` the rows needed for the baseline (top 25% by speed via SQL `ORDER BY ball_speed_kmh DESC`) |
| Polling | Processing page polls every 1 s forever, with no backoff on errors | Exponential backoff (1 s → 5 s), or SSE `/api/jobs/{id}/events` |
| Frontend renders | **M13**: `VideoPlayer` calls `setFrame` on every displayed frame (about 60 renders/s) | Draw the canvas inside the rVFC callback via refs; update the React frame label at about 10 Hz |
| Bundle | Small: no chart or animation libraries; fonts self-hosted | No action needed |
| Memory | **M14**: object URLs never revoked. Thumbnails held as base64 data URLs | Revoke on clear/unmount; use `canvas.toBlob` with object URLs |
| Storage | **[VERIFIED] M6**: about 6.5× the input size kept per analysis | See M6 |

## 5. Database review

* **Schema:**
  * `Job` (status/progress), `Analysis` (summary columns plus `result_json` TEXT), and `Feedback`.
  * `Analysis.id == Job.id` by convention only; there is **no foreign key**.
  * `Feedback.analysis_id` has **no FK** (`PRAGMA foreign_key_list(feedback)` → `[]`), and cascades are done by hand in `delete_analysis`. → M7
* **Indexes:** `Analysis.bowler_name` and `Feedback.analysis_id` are indexed; `Job.status` is not, so the startup recovery scan is a full table scan (fine at this size). Missing a composite `(bowler_name, created_at)`.
* **Query optimisation:** acceptable today, but no pagination on `/deliveries`, `/bowlers` or `/history` (L6).
* **Data consistency:**
  * `result_json` duplicates `result.json` on disk, so the two can drift (only the DB copy is read).
  * NaN was persisted as non-standard JSON **[VERIFIED]**: `{"trim_start_s": NaN}` (M2).
* **Transactions:** each update is its own short transaction (fine). `_save_analysis` and the job's "done" status are two separate transactions; a crash between them leaves an `Analysis` row whose job is never marked done, so `recover_interrupted` then marks it failed. Fix: do both in one transaction.
* **Concurrency:** SQLite runs in WAL mode with `busy_timeout=5000` (good). There is one writer thread plus request threads. Running multiple processes would break the job model (H7).
* **Data integrity:**
  * synthetic sample deliveries are mixed into real history (H5)
  * history drops metric units (H9)
  * timezone handling is inconsistent (M8)
  * no migrations (M7)

## 6. Frontend review

* **State management:** local state per page plus a `SettingsProvider` in localStorage, which is appropriate. `results/[id]` resets the view toggle whenever settings change (minor).
* **Rendering:** M13 (per-frame renders). `TrendChart` re-renders all charts on hover through shared state; acceptable at about 8 charts.
* **Architecture:** clear `lib/api.ts` boundary and typed contract (`types/analysis.ts` mirrors the Pydantic models). Pages are fairly large (`new/page.tsx` 305 lines, `results/[id]` 204 lines). Split out `UploadStep`, `TrimStep`, `ConfirmStep` and `ResultsHeader`.

* **SEO:** every page is a client component, and there is only root metadata. Low impact for a private app; add per-page `metadata` if it becomes public.
* **Security:** no XSS sinks ✔. Missing CSP and frame protection (M5). `NEXT_PUBLIC_API_URL` is inlined at build time ✔ (not a secret).
* **UX:**
  * "Analyze a sample clip" writes into the user's own profile (H5)
  * the upload XHR has no timeout or cancel (L8)
  * theme flash for light-mode users, because the server renders `data-theme="dark"`

## 7. Backend review

* **Architecture:** clean separation, one module per pipeline stage (pure-ish typed functions), `PoseEstimator` interface, rules driven by `benchmarks.yaml`. The orchestrator is long (236 lines) but linear.
* **Error handling:** consistent `{code, message, fix}` everywhere ✔. But unhandled exceptions leak internals (M1), and `_Encoder.close()` can mask the original error (L2).
* **Logging:** the standard `logging` module with no request id, no structured/JSON output and no access-log correlation (M16). Job errors are logged with tracebacks ✔.
* **API design:** REST-ish but unversioned, with mixed resources (`/analysis/{id}` and `/deliveries`). `DELETE` returns a body (fine). `GET /api/health` has a side effect: it creates a landmarker on first call (M16).
* **Middleware:** CORS only. Missing TrustedHost (H3), body-size limiting (H1), rate limiting (H2), security headers (M5) and request ids (M16).
* **Security controls:** see C1–H4.
* **Scalability:** a single in-process worker, a local filesystem and SQLite cap it at one machine and one process (H7). This is acceptable for the stated personal use and is documented as such.

## 10. Detailed findings (requested format)

### CRITICAL

# C1. No authentication on any endpoint
Severity: **Critical** (production) / Low (localhost-only)
Location: `backend/app/api/routes.py`, all routes; `backend/app/main.py`
Description: Every endpoint, including `DELETE /api/analysis/{id}`, `POST /api/analyze` and the video, PDF and frame downloads, is anonymous. There is no user model, no session, no token, and therefore no MFA, JWT or session handling to audit. **[VERIFIED]** An anonymous `DELETE` is processed.
Impact: Anyone who can reach the port can read every bowler's videos (biometric/personal data), delete all data and consume all CPU and disk. OWASP A07 / A01.
Fix: Add an authentication layer. For a single user, a long random API key checked with `secrets.compare_digest`. For multi-user, OIDC (e.g. Auth.js on the frontend, with JWTs verified via JWKS on the backend: check `aud`, `iss` and `exp`, require RS256, reject `alg=none`). Add an owner column (see C2).
Improved Code:
```python
# app/api/security.py
import secrets
from fastapi import Depends, Header
from app.core.config import settings
from app.core.errors import BowlIQError

def require_user(authorization: str | None = Header(default=None)) -> str:
    token = (authorization or "").removeprefix("Bearer ").strip()
    if not settings.api_token or not secrets.compare_digest(token, settings.api_token):
        raise BowlIQError("UNAUTHORIZED", "Missing or invalid credentials.", "Sign in again.", 401)
    return "owner"  # with OIDC: return the verified `sub` claim

# app/api/routes.py
router = APIRouter(prefix="/api", dependencies=[Depends(require_user)])
public = APIRouter(prefix="/api")          # only /health lives here
```
Video `<video src>` cannot send headers, so for media use short-lived signed URLs: `?exp=…&sig=HMAC(id|exp)`.

# H1. Request body size not bounded: the 200 MB check runs after the whole upload is received
Severity: **High**
Location: `routes.py:_save_upload` / `analyze`; Starlette multipart parsing
Description: **[VERIFIED]** A 260 MB upload was received in full (`size_upload 260000202`) before the API answered 413. Starlette and python-multipart spool the entire multipart body to a temp file first; the application check only runs afterwards.
Impact: Disk and bandwidth exhaustion (DoS) with arbitrarily large bodies. OWASP A06.
Fix: Reject on `Content-Length` and count streamed bytes in ASGI middleware. Also set the limit at the reverse proxy.
Improved Code:
```python
# app/core/limits.py
from starlette.types import ASGIApp, Receive, Scope, Send
from starlette.responses import JSONResponse

class BodySizeLimit:
    def __init__(self, app: ASGIApp, max_bytes: int):
        self.app, self.max = app, max_bytes
    async def __call__(self, scope: Scope, receive: Receive, send: Send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)
        cl = dict(scope["headers"]).get(b"content-length")
        if cl and int(cl) > self.max:
            return await JSONResponse({"code": "FILE_TOO_LARGE", "message": "Upload exceeds the size limit.",
                                       "fix": "Upload clips under 200 MB."}, 413)(scope, receive, send)
        seen = 0
        async def limited() -> dict:
            nonlocal seen
            msg = await receive()
            seen += len(msg.get("body", b""))
            if seen > self.max:
                raise ValueError("body too large")
            return msg
        await self.app(scope, limited, send)

# main.py  (2 uploads + form overhead)
app.add_middleware(BodySizeLimit, max_bytes=2 * settings.max_upload_bytes + 1_000_000)
```
Also check free disk before accepting an upload: `shutil.disk_usage(settings.storage_dir).free > 3 * size`.

# H7. Job queue is not safe with more than one process, and loses queued jobs on restart
Severity: **High** (production scaling)
Location: `backend/app/core/jobs.py` (`_executor`, `recover_interrupted`, `submit`)
Description: **[CODE]** The executor lives inside the web process. With `uvicorn --workers 2`, or any second instance:
* each process runs its own queue;
* each process's startup `recover_interrupted()` marks **the other process's running jobs** as failed `INTERRUPTED`;
* jobs still queued in memory are lost on every restart (they are marked failed, never retried).
Impact: Spurious failures, lost work, and no horizontal scaling. OWASP A06.
Fix: Separate the worker process from the web process, and claim jobs atomically in SQLite with a lease and heartbeat. Only reclaim jobs whose lease has expired.
Improved Code:
```python
# worker.py: run as its own process: python -m app.worker
def claim_next(worker_id: str, lease_s: int = 120) -> str | None:
    with get_engine().begin() as c:
        row = c.exec_driver_sql(
            """UPDATE job SET status='processing', worker=?, lease_until=datetime('now', ?)
               WHERE id = (SELECT id FROM job WHERE status='queued'
                           OR (status='processing' AND lease_until < datetime('now'))
                           ORDER BY created_at LIMIT 1)
               RETURNING id""", (worker_id, f"+{lease_s} seconds")).first()
        return row[0] if row else None
# heartbeat: UPDATE job SET lease_until=datetime('now','+120 seconds') WHERE id=? (from the progress callback)
```

# H8. Body-height scale biased low, inflating % height metrics, m/s values and ball speed
Severity: **High** (measurement correctness, core product)
Location: `backend/app/pipeline/scale.py:estimate_scale`; `orchestrator.py` (`frames=np.arange(0, events.bfc.frame + 1)`)
Description: **[VERIFIED]** Height is taken as the 90th-percentile nose-to-ankle distance during the **run-up** only, where the bowler is never fully upright (flexed knees, forward lean).
* On the sample clip the estimate was 322 px against a true value of about 346–360 px (7–11% low).
* So ball speed read **136 ± 3 km/h against a true value of about 122**: the ± excludes the truth (see M19).
Every m/s value and every "% height" metric is inflated by the same factor.
Impact: Systematic error in the headline numbers. Stride can be misjudged as "over-long".
Fix: Estimate height from segment lengths, which barely depend on posture: the per-segment median across all valid frames, with known anthropometric ratios. Carry the scale uncertainty into confidence and `plus_minus`.
Improved Code:
```python
def body_height_from_segments(kin: Kinematics) -> tuple[float, float]:
    """Height ≈ (shank + thigh + trunk + neck→nose) / 0.87 (Drillis & Contini ratios). Returns (px, rel_sd)."""
    seg = lambda a, b: np.linalg.norm(kin.joint(a) - kin.joint(b), axis=1)
    parts = []
    for s in ("left", "right"):
        parts.append(seg(f"{s}_knee", f"{s}_ankle") + seg(f"{s}_hip", f"{s}_knee"))
    leg = np.nanmedian(np.nanmax(np.vstack(parts), axis=0))
    trunk = np.nanmedian(np.linalg.norm(kin.mid("left_shoulder", "right_shoulder") - kin.mid("left_hip", "right_hip"), axis=1))
    head = np.nanmedian(np.linalg.norm(kin.joint("nose") - kin.mid("left_shoulder", "right_shoulder"), axis=1))
    h = (leg + trunk + head) / 0.87
    sd = float(np.nanstd([leg / 0.53, trunk / 0.30, head / 0.13]) / h)  # spread between segment-based estimates
    return float(h), sd
```

## FINAL REPORT

### 1. Executive summary
BowlIQ works end to end:
* 40 automated tests pass.
* The real-browser flow works: upload, live progress, overlay video, PDF, history, compare.
* It produces honest measurements on real footage (your WhatsApp clip: events within about 1 frame of manual review, with unreliable metrics withheld with reasons).
* The pipeline code is cleanly modular, and typed end to end.
* No injection, XSS, path-traversal or secret-exposure issues were found; I tested for them specifically.

However, the application was **designed as a single-user localhost tool**, and it is **not production-ready as a networked service**:
* there is **no authentication or authorization**;
* requests can be forged cross-site, and DNS rebinding can read local data (both verified);
* request bodies and job submission are unbounded (verified);
* the job queue is process-local;
* there are no deployment, CI, backup or monitoring assets.

Two **data-correctness** bugs affect even the local app:
* the sample clip pollutes the user's personal baseline (H5);
* trend charts mix units (H9).

There is also a measurement bias in the body-height scale that inflates speeds by about 7–11% (H8, M19).

### 2. Critical issues
C1 No authentication · C2 Broken object-level authorization (IDOR / enumeration)

### 3. High-risk security vulnerabilities
H1 Unbounded upload body (verified) · H2 No rate limiting or quotas · H3 DNS rebinding / no Host validation (verified) · H4 Cross-site drive-by POST (verified) · M1 Error detail and path disclosure (verified) · M3 Unpinned model download · M4 Untrusted media parsing without hardening · M5 Missing security headers (verified)

### 4. Performance bottlenecks
Pose on CPU (the main cost) · event-loop blocking in `/analyze` (H6, verified) · double video encode · `/frame` decoded on every request with no cache · `no-cache` on immutable videos · per-frame React renders (M13) · about 6.5× storage amplification (M6)

### 5. Architecture concerns
In-process job queue and restart recovery (H7) · SQLite and local disk limit it to a single node · no migrations or FKs (M7) · result stored twice (DB + file) · health check with side effects (M16) · scale estimation design (H8)

### 6. Recommended refactoring (in order)
1. Security middleware stack: TrustedHost → BodySizeLimit → origin guard → rate limiter → auth dependency (C1, C2, H1–H4).
2. A separate worker process with lease-based job claiming (H7); move the blocking calls out of async routes (H6).
3. Ownership and migrations: Alembic, `owner_id`, FKs with cascade, timezone-aware timestamps (C2, M7, M8).
4. Measurement fixes: segment-based scale with uncertainty propagated into confidence and ± (H8, M19); multi-candidate events (M9); an anatomical leg anchor (M10); VFR timestamps (M20).
5. Data fixes: a reserved sample bowler (H5); units in history (H9); input finiteness checks (M2).
6. Ops: Dockerfile, CI, reverse proxy with TLS and limits, backups, metrics (M17, M16).
7. Frontend: split large pages; ref-based canvas drawing; accessibility fixes; CSP (M13, M18, M5).

### 7. Security hardening checklist
- [ ] Authentication (API key or OIDC); signed short-lived media URLs
- [ ] Owner scoping on every query; 404 for objects the caller doesn't own
- [ ] `TrustedHostMiddleware` (localhost / your domain)
- [ ] Origin check plus custom client header on unsafe methods
- [ ] Body-size limit in middleware and at the proxy; disk-free check
- [ ] Rate limits and a per-user queue cap (429)
- [ ] Generic 500 errors with error ids; no paths in `/health`
- [ ] Finite-number validation; `json.dumps(allow_nan=False)`
- [ ] `-protocol_whitelist file` on ffmpeg/ffprobe; magic-byte check; pinned, updated ffmpeg
- [ ] Worker in an unprivileged container, egress only to the Gemini host
- [ ] Pinned model URL and SHA-256; hash-locked requirements; Dependabot; `pip-audit` / `npm audit` in CI
- [ ] Security headers (CSP, frame-ancestors 'none', nosniff, Referrer-Policy, HSTS behind TLS)
- [ ] `--no-server-header`; Next.js `poweredByHeader: false`
- [ ] TLS at the reverse proxy; Gemini key from a secret store, never in images
- [ ] Retention policy and storage quota; encrypted backups; tested restore
- [ ] Structured audit logs for deletes and uploads; alerting on failure spikes
- [ ] Upgrade `setuptools` to ≥ 84.1.0 in build environments

### 8. Production Readiness Score: **40 / 100**
It works end to end with good tests and docs. It is missing auth, abuse limits, multi-process-safe jobs, deployment, monitoring and backups. (As a single-user local tool I would rate it about 75.)

### 9. Security Score: **35 / 100** (network-exposed)
Injection, XSS, path traversal and secrets are clean. Access control, request forgery, DNS rebinding and resource limits are absent. (In its intended localhost-only use, about 60, with H3 and H4 the real local risks.)

### 10. Maintainability Score: **74 / 100**
* Strengths: clear module boundaries, a typed contract on both sides, rules driven by data in YAML, deterministic fallbacks, and 40 tests.
* Weaknesses: no migrations, unpinned dependencies, some long modules/pages, duplicated validation, no frontend tests and no CI.
